Stable Low-Latency CONC Selection

Choose a stable serving point from a concurrency sweep. The goal is not absolute peak throughput, but a reliable low-latency operating point for regression.

Selection Rule

  1. Sweep max-concurrency from low to high.
  2. Run the sweep with no-enable-prefix-caching.
  3. Track output throughput and latency, especially TPOT and TTFT.
  4. Maintain the current best throughput point.
  5. After a throughput peak appears, check the next K points.
  6. If the next K points do not exceed the peak by more than eps, confirm this point.

Default Parameters

K = 5
eps = 1%

C_recommended = first confirmed throughput peak

Why This Point

This avoids selecting a later high-throughput point that only improves throughput slightly while significantly increasing latency. It is designed for stable low-latency regression, not maximum capacity reporting.

A3B example: CONC=53 is followed by CONC=54-58 and none exceeds throughput(53) * 1.01, so C_recommended = 53.

Deriving Regular Test CONC

Apply a safety margin after selecting the stable low-latency point.

C_regular = floor(C_recommended * 0.9)

Purpose

  • Leave headroom for runtime variation.
  • Reduce impact from scheduler fluctuation.
  • Avoid KV cache spike sensitivity.
  • Make regression runs more stable and repeatable.

Example

C_recommended = 53

      C_regular = floor(53 * 0.9)
          = 47
C_regular is the concurrency used by regular performance regression.

Regression Benchmark Configuration

Use a fixed steady-state benchmark shape after deriving C_regular.

max-concurrency = C_regular
max-num-seqs  = C_regular
no-enable-prefix-caching
num_warmups     = C_regular
num_prompt      = 5 * C_regular
request-rate    = inf

Example

C_regular = 47
max-concurrency = 47
max-num-seqs    = 47
no-enable-prefix-caching
num_warmups     = 47
num_prompt      = 235
request-rate    = inf

Why num_prompt = 5 * CONC

It does not increase effective concurrency. It keeps enough pending requests available so the scheduler can run in a steadier prefill/decode interleaving mode, reducing first-wave burst and tail-drain effects.

Why --max-num-seqs = CONC

It aligns the server-side active sequence limit with the client-side concurrency limit. This removes an extra configuration variable, making repeated runs and framework comparisons more reproducible.

This measures stable serving throughput and latency at a controlled concurrency.

When To Re-sweep CONC

For performance regression, keep C_regular fixed. Re-sweep only when the old point stops being a valid probe.

Re-sweep Triggers

  • Expected perf change: a feature intentionally trades performance for functionality, or improves performance enough that the old point is no longer representative.
  • System environment change: device SKU such as B60/B70/CRI, device count, memory size, or major runtime/driver stack changes.
  • Test configuration change: model, TP/PP, dtype, ISL/OSL, prefix caching, or key serving parameters.

Rule

  • Keep C_regular fixed for normal regression tracking.
  • Refresh it only in the three cases above.
Short version: keep one fixed regression CONC, and refresh it only for expected perf shifts, system environment changes, or benchmark configuration changes.

What This Method Measures

The selected regression point is a stable serving point, not a maximum capacity point and not a customer SLA point.

Measures

  • Stable serving throughput.
  • Steady-state scheduler behavior.
  • Decode latency under controlled concurrency.
  • Regression sensitivity across versions and builds.

Avoids

  • Over-selecting an aggressive global peak.
  • Overreacting to single-point throughput noise.
  • Using first-wave burst latency as steady-state latency.
  • Mixing capacity peak with SLA qualification.
C_recommended = first confirmed low-latency peak
C_regular  = floor(C_recommended * 0.9)
num_prompt    = 5 * C_regular
